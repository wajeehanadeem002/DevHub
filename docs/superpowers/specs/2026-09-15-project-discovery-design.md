# DevHub Public Project Discovery Design

## Scope

This phase replaces the landing page's static project previews with real
published project data and adds a dedicated, public `/projects` discovery
route. Visitors can search, filter, sort, and page through published projects,
then open the existing `/projects/[id]` detail route.

Project authoring, public project detail pages, Clerk authentication, profiles,
project images, and row-level security already exist and remain the foundation.
Creating likes or saves, following developers, notifications, moderation,
recommendation algorithms, and deployment remain outside this phase.

## Approved Product Decisions

- `/projects` is the canonical project-discovery route.
- Discovery is server-rendered and driven by URL search parameters.
- Supported parameters are `q`, `category`, `technology`, `sort`, and `page`.
- The default sort is newest first. Users can also sort by most liked.
- Each results page contains at most 12 projects.
- The landing page's Trending Projects section shows up to four real published
  projects ordered by like count, with publication date and ID as stable
  tie-breakers.
- Navbar and footer Explore and Projects links point to `/projects`.
- Existing Mocha + Cream visual language, responsive behavior, keyboard focus,
  and reduced-motion treatment are preserved.
- Like and save counts may be displayed, but interactive like/save controls are
  not added in this phase.

## Route and URL Contract

The route accepts these optional search parameters:

- `q`: trimmed search text, limited to 100 characters.
- `category`: one curated category slug.
- `technology`: one curated technology slug.
- `sort`: `newest` or `popular`; missing or invalid values become `newest`.
- `page`: a positive integer; missing or invalid values become `1`.

Unknown category or technology slugs are treated as inactive filters and are
omitted from links generated by the page. Extra unrelated parameters are
ignored. Filter and sort links preserve the active search text and reset
pagination to page 1. Pagination preserves every active filter.

The route metadata uses the stable title and description for Explore Projects;
filters do not create separate indexable metadata variants. The sitemap gains
the canonical `/projects` URL only.

## Page Experience

The page opens with an Explore Projects heading and short discovery copy. A GET
form contains a search input, category selector, technology selector, and sort
selector. Submitting the form updates the URL and renders server-filtered
results. A Clear filters action appears whenever a non-default filter is active.

The page shows a concise result count followed by a responsive project grid:
one column on small screens, two on medium screens, and three on larger screens.
Each card contains the cover image or existing branded fallback, category,
title, summary, owner identity, curated technologies, and like count. The whole
card links to `/projects/[id]` with an accessible project-specific name.

Previous and Next pagination controls appear only when their destinations
exist. They are ordinary Next.js links so discovery remains usable without
client-side JavaScript. An empty result state explains that no projects match
and offers Clear filters. Provider failures use the existing route-level error
boundary and expose no Supabase details.

## Landing Page Integration

The home page remains visually unchanged outside the Trending Projects data.
Its section becomes async and requests at most four popular published projects.
It uses the same live card presentation and public image URL resolution as the
discovery page. If no published projects exist, the section renders a compact
empty state with a call to create a profile or visit Explore Projects; static
fake projects are not retained as fallback data.

The landing page does not include the full discovery filter form or pagination.
Its section includes a View all projects link to `/projects`.

## Data and Module Boundaries

Route pages remain React Server Components. A server-only discovery module under
`src/features/projects/` owns parameter normalization and public queries. Its
input is a normalized discovery options object; its output contains the project
summaries, total count, normalized page, page count, and curated filter options.

The query always explicitly requires `projects.status = 'published'`, even
though RLS also protects public visibility. This prevents an authenticated
project owner from seeing their drafts in the public discovery surface.
Existing RLS additionally requires a public, non-deleted owner profile.

Search uses the existing generated `projects.search_document` tsvector and GIN
index. Category filtering resolves a category slug to its ID. Technology
filtering resolves the slug and obtains matching project IDs through
`project_technologies`. Sorting is deterministic:

- newest: `published_at DESC, id ASC`;
- popular: `like_count DESC, published_at DESC, id ASC`.

The project page query selects only the requested 12-row range and requests an
exact result count for pagination. If a positive requested page is beyond the
last non-empty page, the data module loads the last valid range and reports that
normalized page. Related categories, technologies, public owners, and first
ordered images are loaded in bounded bulk queries and joined in application
memory. The implementation does not issue one query per card. Public Storage
URLs are derived with the existing project image helper.

The existing public project summary/card contracts are extended with owner and
like-count fields so the developer profile grid, discovery grid, and landing
section can share presentation without duplicating provider logic. Profile
pages keep their existing owner-scoped query and ordering unless a shared helper
can be reused without changing their behavior.

## Validation and Security

- Search text is trimmed, length-limited, and passed through Supabase's
  full-text search API rather than interpolated into SQL.
- Category and technology filters activate only for curated slugs; unknown
  slugs are safely ignored.
- Page values are clamped to valid positive integers and the existing result
  range.
- Public queries select published projects explicitly and continue relying on
  RLS for public-profile visibility.
- Raw provider errors, JWTs, internal Storage paths, and credentials never reach
  the rendered error message.
- No service-role client, write function, or new public database privilege is
  introduced.

The existing schema already has the full-text, publication, category, and
technology indexes required for this MVP. No database migration is planned. If
real usage later shows popular sorting needs an index, that optimization will
be a separate measured change.

## Accessibility and Responsive Behavior

Every field has a visible label. Results and filter controls use semantic
headings, forms, lists, and links. The result summary communicates the active
query without relying on color. Focus states remain visible, card images have
their stored alt text, and fallback covers remain decorative or receive a
project-specific accessible label as appropriate.

Controls wrap without horizontal overflow. The desktop filter row stacks into
a single-column form on small screens, and pagination remains reachable with
large touch targets. Existing reduced-motion classes apply to card hover
movement.

## Cache and Error Behavior

Discovery pages render fresh public data through a server-only anonymous
Supabase client built with the publishable key and no Clerk access token. This
keeps public RLS behavior and result counts identical for signed-in and
signed-out visitors, including when a signed-in owner has a private profile.
Existing project publish, unpublish, update, image, and delete actions will
revalidate `/projects` and `/` in addition to their current targets so public
lists update after mutations.

Input normalization never throws for malformed URL parameters. Provider or
Storage failures throw stable application errors handled by the existing error
boundary. An empty dataset is successful state, not an error.

## Testing and Verification

Implementation follows test-driven development. Tests cover:

- search-parameter trimming, limits, defaults, and page normalization;
- explicit published-only query behavior for signed-out and signed-in clients;
- full-text search, category filtering, technology filtering, both sort modes,
  deterministic tie-breakers, and the 12-item range;
- bounded related-data loading without per-card query loops;
- result count, empty state, Clear filters, pagination URL preservation, and
  responsive grid semantics;
- project card owner, technology, cover/fallback, like count, accessible link,
  and detail-route destination;
- landing top-four ordering, empty state, and View all projects link;
- navbar, footer, sitemap, and mutation revalidation updates;
- safe provider-error conversion.

Final local verification runs:

- `pnpm.cmd lint`
- `pnpm.cmd typecheck`
- `pnpm.cmd test`
- `pnpm.cmd build`

The production server is restarted and `/` plus `/projects` are checked for
successful public responses. No Git operation, deployment, Playwright browser
installation, screenshot, or QA artifact is part of this phase.
